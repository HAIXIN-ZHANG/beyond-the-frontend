## 1. Reader problem and goal

Reuse G01's fictional course site and move the focus into the browser. Compare opening search with no title yet, and seeing the title/search field but receiving no timely feedback after pressing Search. Users can call both “slow,” but they require different investigation.

After this chapter, readers with page/API experience should be able to:

1. Explain the relationship between HTML, DOM, style, layout and screen output without equating a received file with a usable feature.
2. Trace resource availability → code execution → presentation through one load and one search.
3. Separate resource waits, busy-main-thread work and missing/failed readiness, and identify necessary evidence rather than diagnose from a screenshot or one request duration.
4. Understand the browser model needed for later layout, component and rendering-strategy decisions without memorizing internals or event-loop puzzles.

**Editorial judgment:** although the working title asks what happens before the page appears, explain one subsequent interaction to answer the second question. Make that extension clear in the opening.

## 3. Research and key claims

The original research opened and read the specified body sections on **2026-11-15**, not each entire standard or merely search summaries. HTML Living Standard pages displayed 2026-11-14 as their update date. A rolling standard is not proof every browser implements every detail. Official developer explanations support a common implementation/observation model, not cross-browser experimental proof. Use only citations needed by the prose; retain the complete comparison here.

| Source / claim | Primary or official sections read | Conditions and evidence boundary |
| --- | --- | --- |
| S1: HTML is input; DOM is a parsed, script-modifiable document representation | [WHATWG HTML §13.2.1 Overview of the parsing model, §13.2.3 The input byte stream, §13.2.6 Tree construction](https://html.spec.whatwg.org/multipage/parsing.html#overview-of-the-parsing-model) | Normative mechanism: character input passes through tokenization/tree construction. Explain tags/relationships becoming operable nodes, not tokenizer states or DOM as a screenshot. |
| S2: Script modes change fetching/execution timing, not execution into a background JS thread | [WHATWG HTML §4.12.1 The script element, async/defer modes and §4.12.1.1 Processing model](https://html.spec.whatwg.org/multipage/scripting.html#the-script-element); cross-check [MDN script Attributes](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script#attributes) | Limit the table to parser-inserted external classic scripts in initial HTML: ordinary scripts pause subsequent parsing for fetch/evaluation; defer fetches alongside parsing, runs after parsing in document order; async runs when available without a dependable relative order. Modules and dynamic insertion have different rules. |
| S3: Render-blocking and parser-blocking are different dependencies | [web.dev: Understand the critical path, Render-blocking resources / Parser-blocking resources](https://web.dev/learn/performance/understanding-the-critical-path#render-blocking-resources) | Use an enabled head stylesheet matching current media to explain initial rendering waits while HTML can continue parsing. Do not generalize to all CSS everywhere or claim parsing pauses stop every fetch; scanning can discover resources ahead. |
| S4: Updates involve style, geometry, paint and compositing; not every change repeats all work | [web.dev: Rendering performance, The pixel pipeline and three paths](https://web.dev/articles/rendering-performance#the_pixel_pipeline) | Teaching model, not a universal internal structure. Layout determines geometry; paint prepares visual drawing, rasterization produces pixels, compositing combines surfaces. Width may affect neighbors; color can avoid layout. Scope/optimization depend on implementation/page; transform is not guaranteed to avoid paint, nor does all work run on the main thread. |
| S5: Tasks/microtasks/presentation are not “paint after every task” | [WHATWG HTML §8.1.7.1 Definitions and §8.1.7.3 Processing model, microtask checkpoints/rendering opportunities](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model) | Multiple task sources/queues, not one global absolute FIFO. Checkpoints continue handling pending microtasks; rendering depends on opportunities and document conditions, not every assignment. Exclude reentrancy and cross-agent scheduling. |
| S6: Sustained main-thread work can delay interaction; 50ms defines a long task, not guaranteed good experience below it | [web.dev: Optimize long tasks, What is a task? / What is the main thread? / Break up long tasks](https://web.dev/articles/optimize-long-tasks#what_is_the_main_thread) | Main-thread-dependent handling can be delayed. No complete optimization-API tutorial. Scrolling may continue on a compositor thread; “stuck page” does not mean all browser activity stops. |
| S7: An async function does not move synchronous computation away | [MDN async function, Description: synchronous work before the first await and later continuation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function#description) | Adding async does not parallelize CPU work; await suspends the function's continuation without promising a displayed frame. Use minimal syntax; full Promise/error semantics belong in F08. |
| S8: Loading milestones do not universally prove product readiness | [MDN DOMContentLoaded, body and Checking whether loading is already complete](https://developer.mozilla.org/en-US/docs/Web/API/Document/DOMContentLoaded_event) | Parsing and deferred/module-script milestones do not wait for images/async scripts; CSS can affect script dependencies indirectly. Do not infer complete application data, a particular installed listener or absence of later busy work. A short sidebar suffices; avoid an index of metrics. |
| S9: Workers are separate execution contexts without direct page-DOM access | [MDN Using Web Workers, Web Workers API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers#web_workers_api) | Qualify “JS is always one thread.” Messages can connect contexts; page code still updates DOM. No Worker implementation or recommendation to move every task there. |
| S10: Timelines provide evidence, not a complete diagnosis from one duration | [Chrome Network reference, request timing and phase explanations](https://developer.chrome.com/docs/devtools/network/reference#timing-explanation); [Performance panel, Capture and analyze a performance report](https://developer.chrome.com/docs/devtools/performance/overview#capture-and-analyze-a-performance-report) | Chromium observation entry points. TTFB includes a network round trip and response preparation, not server computation alone; Content Download can also reflect browser reading delays. Load/runtime records and screenshots can be aligned, but none ran in F01A: no invented trace or numbers. |

### Simplifications and adopted wording

- The original research also read [MDN How browsers work, Parsing / Render](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work#parsing) as a navigation aid. Its brief async wording can suggest evaluation is nonblocking; use S2's scoped modes instead.
- The introductory linear DOM/CSSOM/render-tree explanation and combined paint/raster language need S4's distinctions. Do not require memorizing engine trees or imply unconditional GPU speedups.
- There is no universal moment when all interactions switch on after HTML appears. Links, inputs and forms have native behavior. Give readiness conditions only to the specific search enhancement; hydration detail belongs in F10.
- Do not adopt whole-page relayout on every DOM edit, a guaranteed loading frame after await, or callbacks guaranteed immediately after network completion. State supported dependencies/possibilities; exact visible timing requires observation.

## 5. Original cases, diagrams and implementation windows

### E1: one course-search page, three different waits

**Teaching assumptions:** ordinary desktop browser, visible foreground tab; initial HTML has title/input/static cards; head references applicable external CSS. External JS installs a handler on a `type="button"` search control. Initially disabled, the control is enabled after successful installation; the input retains native behavior. No backend, permissions, cache or search-ranking implementation.

| Path | Only changed condition | Difference to explain | Invalid inference |
| --- | --- | --- | --- |
| E1-A: resource unavailable | Artificially delay head CSS against normal load | Parsing, resource waiting and visibility are different events; exact first presentation is conditional | Blank proves slow CSS, or every image blocks first render |
| E1-B: enhancement pending/failed | Delay/reject search JS with normal CSS/HTML | Content may appear first while this control stays disabled; inspect Network/Console, not elapsed time alone | Every native interaction fails, or DOMContentLoaded/appearance proves listener installation |
| E1-C: ready behavior, delayed handling | After installation/enabling, deliberately trigger long synchronous work and try search during it | Listener presence does not guarantee immediate execution; previous content can remain visible | Clicks must be permanently lost, every native input must stop, or the entire browser is blocked |

E1-C deliberately injects a fault; it is not a benchmark for real course-data size. Fixed iteration counts cannot guarantee duration across devices. Any later numeric duration needs actual environment and measurement evidence.

### E2: text color versus available width

Change only the color on one card, then separately reduce its available width until a long title wraps. The first can avoid new geometry; the second may change card height and later positions. Explain affected scope rather than whole-page relayout/repaint every time. Avoid simultaneous fonts/images/animations so the comparison has one variable.

### E3: why did “searching” not appear in time?

The candidate conceptual sequence is set feedback → long synchronous filter → write results in one handling period. The intermediate feedback is not guaranteed to become a displayed frame. Contrast waiting for a real async request: the main thread may do other work while waiting, but later long computation can still block it.

Do not prewrite runnable code or present `await Promise.resolve()` / `setTimeout(..., 0)` as a verified fix. Pseudocode plus a timeline can explain the mechanism. If runnable material is required, confirm its F01M file/evidence scope and perform V3 before making observed claims.

## Stable fictional contract

Assume one submitted search at a time and a small public course catalogue without pagination or partial results. The service searches the currently published catalogue; it does not search every course in existence. Filtering/permission enforcement, if the product later requires private data, remains server responsibility. The response is for the currently submitted criteria; stale/out-of-order responses are a separate interaction lesson, not solved by this contract. A result does not guarantee seats, enrollment eligibility or future availability.

- Example request: `GET /api/courses?q=HTTP&level=intro`. `q` is the title keyword, trimmed and required to be nonempty; `level` is an optional exact filter, either `intro` or `advanced`, with omission meaning both. Both conditions apply together. Define `intro` as the catalogue's introductory classification, not an independent guarantee of suitability. Reject an empty normalized keyword or an unsupported level rather than silently reinterpret it.
- On successful search, HTTP200 carries a JSON object with required `items`, an array of all matches in this small catalogue/query scope. Each entry has required nonempty string `id` (course identity, not row number) and `title` (display title). The example `{"items":[{"id":"c-17","title":"HTTP 入门"}]}` demonstrates the happy path; do not invent total/order/relevance/snapshot guarantees.
- A successful search with no matches returns HTTP200 and `{"items":[]}`. Empty describes this query's catalogue scope/conditions; it does not imply an error, a nonexistent catalogue or an empty universe.
- A temporary planned service-maintenance case returns HTTP503 with an application-defined body such as `{"error":{"code":"SEARCH_UNAVAILABLE"}}`. That body is not a successful search result; neither code name nor HTTP503 is a universal API schema. No guaranteed recovery time, automatic retry or provider choice follows. A query failure from another cause also must not be rewritten as an empty list.
- Invalid request parameters receive an explicit refusal appropriate to the input; the page can explain which condition needs correction. No HTTP-error taxonomy is needed. A non-JSON/ill-shaped success body is a response-contract failure, not a successful zero-match query.

Explain one normal journey: page collects criteria → request handler validates/interprets them → query obtains matching published records → service maps records into agreed result fields → page checks/interprets the result and shows titles. Internal table/model field names need not be the public response names. This is a stipulated small teaching design, not inspected repository code or proof of a service implementation.

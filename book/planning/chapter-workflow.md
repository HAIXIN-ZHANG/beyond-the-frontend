# 逐章流程：先分析 review，再写正文

更新：2026-11-14。负责人：Writer。

**用户已确认的流程要求：** 此后每章先认真分析和调研，列出具体小节与讲解细节，提交给项目主审 agent review；收到反馈并处理后，再进入正文创作。正文完成后仍保留原有阶段 review。本文件落实这一写作要求，不放行未确定的章节、全目录、依赖安装或发布。

## 谁来做

- Writer 负责调研、分析稿、细纲、正文、必要验证和修订。
- 项目主对话作为主审，检查分析是否足以支撑正文，以及成稿是否准确、连贯、适合目标读者。
- 用户决定目标与范围，是最终决策者。Developer 只在需要协调内容呈现时参与，不替代内容 review。
- “analyzer”在此指**正式的章节分析交付**，不是新增常驻 agent。当前不创建新 agent、不恢复 Fact checker。

## 每章的两个 review 关口

| 步骤 | Writer 的交付 | 继续条件 |
| --- | --- | --- |
| 1. 确定范围 | 本章问题、读者前置、所属任务、允许改动文件 | 用户或主对话已明确本章范围；不能仅凭全书目录启动全部章节 |
| 2. 分析与调研 | 官方/原始来源、关键主张、边界、知识依赖、候选例子、必要验证计划 | 形成足以评估的证据与解释路径，不以搜索结果清单代替分析 |
| 3. 提交分析稿 | 按模板整理的 analyzer，含详细小节和取舍 | 发给现有项目主审，等待实际反馈；此时不写完整正文 |
| 4. 分析 review 与修订 | 逐项处理意见，必要时补来源或缩小范围 | 主审明确接受分析和本章写作范围；有阻塞项则先修订/复审 |
| 5. 写正文与自查 | 按接受的分析写完整章节、必要图示/代码及验证证据 | 分析与原理一致；新增实质问题按下文返回分析 |
| 6. 正文 review 与修订 | 阶段交接、实际正文、与分析的差异和实际检查 | 主审明确通过；不以分析通过代替成稿通过 |
| 7. 仓库同步或下章 | 精确文件清单与 Git 协调；下一章单独范围 | 按适用用户授权执行；不得自动合并、部署或全书连续生成 |

review 是实际检查和明确结论，不是等待一段时间、发出消息或收到“已收悉”就算通过。Writer 不自行给自己的分析或正文打通过标记。

## 分析稿必须讲清什么

1. **本章为什么存在：** 读者会遇到的具体困惑，读完能解释或判断什么；不只写一个技术名词。
2. **知识边界：** 默认知道什么，哪些先解释，哪些引用前章，哪些留给后章或可选深入；避免重复和突然跳级。
3. **调研结论：** 原始来源与查阅日期、支持的具体主张、适用版本/条件；区分事实、建议、教学假设和未验证项。注明只看了目录/摘要的资料，不能冒充通读。
4. **详细小节：** 暂定标题、要回答的问题、讲解顺序、关键原理、例子/图示、取舍与边界；同时说明为何采用这一顺序。
5. **教学设计：** 熟悉场景如何建立直觉，哪里需要准确机制，类比何处失效；成功、失败或结果未知的路径按主题需要覆盖。
6. **实现与验证：** 必要的技术窗口、代码或图示要证明什么，计划怎么查；未运行就写未运行，不为填表安装依赖或执行外部服务。
7. **AI 与双语：** AI 只在有助于本章时出现；提问卡不是强制项。英文改写是否另有授权，哪些词语/类比需要适配，不自动开始翻译。
8. **待主审判断：** 真实不确定项、对网站/其他角色的依赖、需接受的范围；每条能看出对写作的影响。

范围要与主题相称：分析应足够具体，但不强制收集固定数量来源、框架或小节，不为制造厚度重复成熟概念。

## 文件与版本

- 正式分析稿保存在 `book/planning/analyses/`，以章节工作标识建立单一文件；名称和标识在任务确定时记录，不在本文件预造全书路径。
- 使用 [章节分析模板](templates/chapter-analysis.md)。模板中的示例占位不是已经完成的调研或检查。
- 分析 review 与正文 review 各自使用明确任务标识，写入阶段交接；review 文件仍由主对话维护在 `docs/reviews/`。不复用已结项 W02，也不因本流程擅自占用候选 W03。
- 提交时在交接记录分析稿的文件路径、修订号和适用任务。主审反馈对应同一修订；重大修订后重新确认，不把旧结论自动套到新内容。
- 当前全书目录编号仍是提案，分析文件的工作标识不等于已经确定网站 slug、语言路径或 metadata schema。
- 临时线索可用 `.local/notes/writer/`，但主审需要依赖的结论、来源和未决项必须进入正式分析稿。正文引用的技术事实也应有相应来源，不能只留在内部分析中。

## 反馈与返修

提交分析时发给主审的消息应包含：授权范围、分析稿路径与修订号、详细小节位置、证据/未决项、希望检查的问题，以及“当前未写正文”。请主审把意见写到 review 文件并回传可执行的修订 prompt。

收到意见后，Writer 先阅读完整 review，按项记录处理位置与检查结果。通过后才写正文；若主审只提出建议而未明确是否可以开始，先同步缺少的结论，不把沉默作为许可。

写作中发现新的重要机制、证据冲突、案例业务语义变化，或需要扩大技术/文件范围时，先更新分析并交回相应问题 review。句式、段落节奏与一般措辞可以正常编辑，不为每个标点单独发起审查。

正文交接要说明是否遵循已接受细纲，哪些地方有变化，哪些检查真实执行，哪些还没有。分析稿不能冒充正文，也不能用一份摘要替代实际文稿 review。

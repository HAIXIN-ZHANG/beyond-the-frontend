# 请求出门以后，谁签收了它？

点下搜索，浏览器的网络面板多出一行。你把手指放到这行最右边，那里写着一段等待时间。做服务端的朋友恰好坐在旁边。他还没来得及打开日志，脸上已经有了被点名回答问题的神情。

假设学员第一次访问我们的课程站，浏览器手头还没有可复用的连接。它先要从域名得到可连接的地址；DNS 的结果可能有缓存。然后建立连接，在 HTTPS 下协商加密并检查对方的证书。到了可以交换 HTTP 消息的时候，页面才有机会提出“找标题含 HTTP 的入门课”这个具体请求。再次搜索若能沿用连接，前面这几步未必重走。你在面板里看到的一整段时间，不能全记在写查询的朋友头上。

## 门口收到，和教室收到

请求到了站点入口，接住它的可能是代理或负载均衡器。它依据主机名和路径等规则选应用。应用看明白查询条件，去数据源找课程，整理成回复，再从入口送回浏览器。每一步都可以留下不同的证据。域名解析失败时，应用日志通常连这位访客都认不出来；入口找不到健康的上游时，它可能自己回了错误；应用有一条“已收到”的日志，也只说明请求到了那一层。

比如浏览器报超时，应用却记着这次搜索在稍后完成。两句可以同时为真。沿同一请求标识核对开始和结束位置，才有机会解释中间花了什么时间。你若只拿到浏览器这一端，能说的是“在约定的等待时间内没取得结果”。把鼠标停在那行数字上，它没法替你去机房问话。

普通搜索适合学员问一次、服务答一次。讲义转换可能要等得久些，让页面隔一会儿带任务编号来查，简单，也会产生几次“还没好”的请求。若同一页面需要持续收到进度，服务端推送事件（SSE）可以沿一条连接往浏览器送更新；两边都需要频繁独立发消息时，还可考虑 WebSocket。外部转换商没有开着我们的网站，它办完后向我们的接收端发一笔通知，才是 webhook 那种走法。选哪条路，先看谁有新消息、谁能主动找谁，再算维持连接、断线重连和补漏的代价。

## 第二页怎么又有那门课

下一篇《没有找到课程，还是没有查到结果？》里的目录很小，一次就能返回全部匹配项。先把眼前的目录变大，大到要分好几页，看看会发生什么。设课程按发布日期从新到旧排好，编号作同日的固定次序，依次叫甲、乙、丙、丁。每次取两门。第一页已经把甲乙交给学员，有人这时发布戊，排在最前。

先把学员已经看到的甲、乙记在纸边。戊插进来以后，眼前的目录变成戊、甲、乙、丙、丁。若第二页的意思是“跳过眼前最前面的两门”，跳过戊、甲，得到乙、丙。学员还以为手机滑回去了：乙刚刚看过，丁倒一直没有见着。

也可以让第一页附上一个游标，记住最后那门乙的排序位置。学员带着它回来，仍按同样的条件和排序，从乙之后取两门，这次拿到丙、丁。新来的戊排在前头，两页翻完也没见到它，这正合这条约定。要是课程本身改了排序位置、被删掉，或学员换了筛选条件，这张书签就不能担保两页拼得出同一瞬间的目录。真要打印某一刻的完整名录，还得另约快照或固定版本，以及保留到什么时候。

接口有旧调用者时，改约定还得有人回去探望他们。加一个可选的下一页标识，原来只认 `items` 的页面或许能忽略它，可原契约曾承诺一次给全，现在即便老页面继续正常解析，也会悄悄少显示课程。可以保留原入口，另给新分页形式，或先让调用者明确选择分页，再逐步迁移。把请求组织成资源操作、远程方法调用或可以选择字段的查询，都还要面对同一问题：过去读到这份答复的人，今天会得出什么结论？带着它回到那个小小的搜索框，就知道为什么值得为一个空数组认真写上几句话。

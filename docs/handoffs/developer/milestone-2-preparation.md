### Location identity and precedence

Store `(locale, chapterId, headingId, sourceHash)` rather than raw URL, scroll pixels, paragraph ordinal or manuscript path. Resolve routes afresh through the current allowlist and `chapterPath`/`withBasePath`; encode a validated heading fragment once. Render current approved labels as text. Persist no selected passage, query string, private URL, manuscript body, access token or device identifier.

Chapter ID is stable only by editorial/publishing convention. Current heading IDs are **deterministic, not edit-stable**: `markdown.ts:43–48` derives them from normalized text and collision suffixes. Renaming/reordering duplicate headings can change or reuse an ID. First slice must therefore use conservative hash validation, not promise durable paragraph anchors or add a hidden permanent-ID schema.

1. Incoming route plus any explicit fragment wins over stored state, including on refresh/back/forward. A malformed or missing fragment does not authorize a jump to some saved location. Existing browser/native navigation stays in charge.
2. Without a fragment, direct chapter entry starts normally; no automatic restore, scroll or focus after hydration. Only a deliberate Continue/bookmark link applies a stored target. There is no theme-head reading-state script.
3. Continue/bookmark resolves current approved chapter and heading before generating a normal anchor destination. Same hash+existing heading gives exact native section navigation/focus. A chapter-level record resolves to current chapter start.
4. Any source-hash change conservatively offers current chapter start with “content changed” context, even if a string-equal heading ID survives. Missing heading also falls back to chapter start; removed/unpublished chapter offers the existing Chinese index. Do not silently redirect to the next chapter or guess a renamed heading by fuzzy text. A future reviewed alias strategy can improve precision separately.
5. Old bookmark intent stays visible as changed/unavailable until deliberate removal/re-save; do not silently delete it or rewrite its source revision. A new reader checkpoint may replace last position after renewed reading, independently of bookmarks.

### When last position changes; focus remains independent

Last position is one automatic checkpoint; bookmarks are multiple explicit reader choices. Do not turn every visited heading into a bookmark or make scrolling update the browser hash/history.

- Hydration, rendering, background tabs, a storage event and merely opening/closing a control never overwrite a saved checkpoint. Initial read hydrates local UI only; it cannot supersede an incoming shared fragment or an older useful place before the reader acts.
- On visible, active reader input, choose the current real heading at or immediately above the upper reading line, in DOM order; before the first section use the current chapter H1. Respect the measured toolbar/scroll margin, not a duplicated hardcoded offset. Only a **changed** target is scheduled, with a proposed maximum of one persistence write/second; short-lived pending updates remain in memory.
- Arm viewport recording from actual reading wheel/touch/page-scroll keys outside editable/chrome controls, or a deliberate native section/outline/search-result destination. Suspend while search/dialog, Appearance or expanded reading navigation owns interaction. Resume from a fresh reader gesture. Programmatic scroll/focus solely to reveal the Header or restore a disclosure must not replace a prior section with H1. This requires a real combined-flow regression, not an observer-only unit test.
- A validated native fragment navigation may checkpoint that actual target after it exists, without changing its focus. Never call `preventDefault`, `scrollIntoView` or focus() merely to observe progress. Cancel pending writes when remote clear/replacement is observed. A hidden/unloading stale tab must not flush old progress over a newer active tab; teardown is best effort, not the sole saving mechanism.

### Storage shape and bounded failure semantics (proposed)

Recommend browser `localStorage` with an independent project namespace, not the theme key or a new database. One `vctw.reading.v1.last` key holds last position; each explicit bookmark has its own `vctw.reading.v1.bookmark.<encoded-identity>` key. Encode the `(locale,chapterId,headingId)` tuple unambiguously, check key/value identity, and use a versioned record with the public location fields plus a finite `updatedAt`/`savedAt`. A nullable heading means chapter start. Keys are project-specific, not deployment-prefix-specific; paths are rebuilt for root/Pages. A new origin/domain naturally has separate state.

Separate bookmark keys avoid unrelated bookmarks being lost when two tabs save different sections. An array in one shared key is simpler but permits whole-list lost updates; IndexedDB transactions are excessive for this slice. Same-target bookmark add/remove and the single last-position key use last successful write wins; timestamps are display/order hints, not cross-tab clocks or transaction guarantees. The suggested50bookmark capacity below is a UI limit, not an atomic cross-tab quota: simultaneous distinct saves can exceed it temporarily; reconcile the count and prevent further additions without silently deleting successful saves.

| Condition | Proposed response |
| --- | --- |
| Missing/cleared state | Ordinary reading works. No Continue target; empty saved list explains the local scope without fabricated progress |
| Invalid JSON/type/version/oversized record or unsafe identity | Reject without navigation or HTML rendering. Validate against a small runtime schema and current public catalog; never follow a stored URL. Ignore an invalid individual bookmark, expose recovery if necessary, and do not overwrite an unknown-version record automatically. Suggested bounds:4KiB/record,50explicit bookmarks; reaching the limit reports it without evicting existing saves |
| Valid shape but removed chapter/heading or changed source | Preserve the distinction from corrupt storage; show the conservative current chapter/index fallback above. A version mismatch is not automatic migration permission |
| Storage getter/read throws, access denied or quota/write fails | Static reading/search/theme continue. Keep optional session-memory state and honestly announce “this tab only / could not save”; never announce a persistent bookmark before setItem succeeds. Do not repeatedly write on every scroll after a failure; an explicit retry can probe again |
| Remove / clear | Remove individual owned bookmark keys; explicit Clear reading data removes only reading-state keys, leaving `btf.theme` and other origin data untouched. Clear cancels pending capture writes. Guard every removal; report partial failure rather than pretending it cleared. Clearing several keys is not atomic; re-read so a simultaneous new save is not falsely reported absent |
| Cross-tab | Guard `storageArea` against the acquired localStorage reference, like the accepted theme fix; ignore sessionStorage/unrelated keys. Apply add/remove/clear to list/Continue UI and notify same-tab subscribers explicitly. Never auto-scroll, move focus, reopen a dialog or echo-write merely because a remote tab changed state |

Use a small pure validator/resolver plus one client store/controller with stable snapshots and balanced subscriptions, reusing the current theme hook's architectural pattern without sharing its window-global bootstrap. A compact build-derived **public locator projection** (ID/locale/slug/title/hash/actual heading IDs+labels only), passed as server props, is enough to validate Continue/list targets; keep FS/parser AST and review/source paths out of client state. This is derived data, not a new authored chapter schema or copied body. Bound and measure its payload at implementation; there is no reason to fetch manuscripts or the Chinese search index from the English entry, or build a global state framework.

Platform facts were checked against [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) and [MDN storage events](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event) on2026-11-17: storage is origin-scoped; denied access can throw; cross-document events do not notify the writing window. Persistence is not guaranteed after browser/private-mode cleanup. Suggested disclosure: “Saved only in this browser on this device; clearing site data may remove it.” Final bilingual copy and error/clear interactions still need design review. No account, cross-device sync, tracking backend, offline promise or cloud backup is implied.

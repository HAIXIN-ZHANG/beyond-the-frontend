## Required revisions before submission

### R1 · P2: rejecting this submission does not establish no current registration

Location: `book/drafts/zh/01-a-page-and-a-system.md:161–168`, compared with lines 25, 99 and 192.

The state diagram's confirmed-rejection feedback and qualification about this operation not producing a valid registration described the current action only. They did not establish that no previous successful record existed. A successful registration followed by a lost response could be retried and rejected as a duplicate; reporting only rejection still leaves the user unsure of current registration. This was an insufficient distinction, not an allegation that the draft explicitly required an incorrect rule.

Minimal revision: connect the examples with a concrete sentence. An existing valid registration means duplicate rejection should not be interpreted as currently unregistered; show the current business state supplied by the interface or query it. State which action was rejected, preserving unknown where the authorized query/result is inconclusive. Adjust only necessary diagram labels/notes, without expanding into HTTP codes, permission leakage or a full idempotency implementation.

Acceptance: readers can explain a first success/lost response followed by duplicate rejection, without conflict between diagram, prose and task excerpt.

### R2 · P2: an empty query does not establish terminal failure of the earlier request

Location: foundations lines 199–205, related to 89–101.

The draft handled query failure, but needed the boundary of an empty result. The original operation might still be processing; a query can return no record before that operation commits, even against the primary database without replicas/caches.

Minimal revision: a short example distinguishes a found valid record from a temporary absence while an operation may still run. If the interface gives an explicit terminal state, follow that contract; otherwise retain uncertainty. Do not invent an absolute ban on showing unregistered, or require task storage/polling implementation in this chapter.

Acceptance: distinguish current query visibility from the earlier operation's final failure, while preserving ordinary queries' ability to show current state.

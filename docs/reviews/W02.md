## 提交前修订

### R1 · P2：区分“拒绝这次提交”和“当前没有报名”

位置：`book/drafts/zh/01-a-page-and-a-system.md:161–168`，并对照 25、99、192 行。

问题：状态图“确认拒绝 → 显示原因”以及“这次操作没有形成有效报名”的限定，只约束当前操作，不能说明数据库里没有此前已成功的报名。响应丢失后重试，系统可能因记录已存在而拒绝新增；若界面只据此显示拒绝，用户仍不知道自己实际已经报名。这里不是说现稿明确写了错误规则，而是当前图和解释没有把两个事实区分到足够清楚。

最小修正：用一句具体说明连接两个案例——如果已存在有效报名，重复提交不应被解释为“当前未报名”，应按接口返回的当前业务状态展示已报名或转入查询。说明拒绝的是哪次动作；有权查询但结果不明时仍保留未知。必要时只调整状态图标签/注释，不展开 HTTP 状态码、权限泄露细节或完整幂等实现。

验收：读者能回答“第一次成功但响应丢失，第二次因重复被拒绝，用户当前是否已报名”，且图与文字、任务说明片段不冲突。

### R2 · P2：查询没有记录，不自动证明先前请求已经失败

位置：`book/drafts/zh/01-a-page-and-a-system.md:199–205`，联系 89–101 行。

问题：本节正确处理了查询失败，但“取得当前报名记录，再决定怎样呈现”还需要说明无记录这一结果的边界。原报名请求可能仍在处理，查询先返回暂无记录，随后原请求才提交成功。即使查询主数据库也有这种先后顺序，不必引入副本或缓存才能发生。

最小修正：补一个短句或两三句的小例子——查到有效记录可以确认当前已报名；暂时没查到，若原操作仍可能处理中，就不能单凭它宣告该操作最终失败。接口若能明确给出操作终态，则按其约定处理，否则继续表达待确认。不要把“永远不能显示未报名”写成另一条绝对规则，也不要要求在本章实现任务记录或轮询系统。

验收：清楚区分“此刻查询看不到记录”与“之前提交已确定失败”，保留普通查询可展示当前状态的合理性。
